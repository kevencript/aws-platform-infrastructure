# 2. IAM authentication instead of passwords for the data stores

Status: accepted

## Context

The API uses PostgreSQL, Redis and Kafka. No password may appear in code, in a plan or
in the state, and the database credentials must live in Secrets Manager. With provider
5.x, any password Terraform generates or sets ends up in the state, and write-only
arguments need Terraform 1.11, above the supported floor of 1.5.

## Decision

- **PostgreSQL master user:** RDS generates the password, keeps it in a Secrets Manager
  secret encrypted with a key of its own, and rotates it. Terraform holds only the
  secret's ARN.
- **API to PostgreSQL:** IAM database authentication as a database user without
  privileges on the master account. A migration job, the only reader of the master
  secret, creates that user with `GRANT rds_iam`.
- **API to Redis:** an ElastiCache user of type `iam`, over TLS.
- **API to Kafka:** SASL/IAM over TLS, the cluster's only listener.
- Each module publishes the smallest policy its clients need; the root module binds
  those policies to one IRSA role per Kubernetes service account.

## Alternatives considered

- **The API reads the master password from Secrets Manager.** Simpler, but the API would
  run as the master user and hold a long-lived credential.
- **A separate application password in Secrets Manager.** Common, but the password would
  be generated by Terraform and stored in the state.
- **Redis `auth_token`, Kafka SASL/SCRAM or mutual TLS.** Each needs a secret or a
  certificate to store and rotate.

## Consequences

- The API holds no long-lived credential; its tokens last 15 minutes.
- The application must generate IAM tokens for PostgreSQL and Redis and refresh them, and
  Redis connections are dropped after 12 hours.
- IAM database authentication costs instance memory and limits the rate of new
  connections.
- `rds_iam` must never be granted to the master user, or its password stops working.
